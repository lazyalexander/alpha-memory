# 从论文验证方法到 alpha-memory：采纳理由、落地方式与预期效果

[English](paper-rationale.md) · **简体中文**

核对日期：2026-11-16。实现与实验基线：核心仓库 `a8df593`，研究仓库 `a852d04`。

**我们采纳的是“让结论携带可复查的成立条件和证据”这一研究方法，并把它转化为跨会话记忆的工程假设。** 论文没有提出 alpha-memory 的数据库、版本图或补读规则，也没有证明这些机制能改善语言模型。本文分别说明原文事实、我们的设计判断、已有结果和待验证预期。

## 一、论文的主要观点是什么

本报告以仓库引用的 *A Proof of the Most Informative Boolean Function Conjecture* 为主，固定到 [arXiv:2609.24931v2](https://arxiv.org/abs/2609.24931v2)，不把未固定版本的网页视为长期依据。

数学问题是：均匀随机比特串经过独立翻转噪声后，原串的一个布尔输出最多保留多少信息？作者主张对任意维数和布尔函数证明

$$I(g(X);Y)\leq 1-H_2(p),$$

其中 $p$ 是翻转概率，$H_2$ 是二元熵；只读取一个输入坐标的函数可达到该界。证明经局部 Bellman 不等式归约，再结合解析论证与计算验证。[摘要及定理 1.1](https://arxiv.org/html/2609.24931v2)

与本项目直接相关的方法事实有两项：计算验证针对明确区域，覆盖检查与区间算术检查分开，抽样点不代替整区域认证；研究中的反例推翻一个更强推广，并未推翻其所针对的原主要猜想。[原文第 18 节及第 4 部分](https://arxiv.org/html/2609.24931v2)

作者还发布了 Lean 形式化及复核说明；**本项目没有执行该证明的独立重建**。[作者的形式化仓库](https://github.com/dpwoodru/general-courtade-kumar-lean)

这里要区分研究过程与最终论文主张。此前 README 对“原猜想仍开放”的表述容易把某个研究阶段当成最终结论；本次予以修正。论文涉及的多智能体研究框架另有 [Stellar Colosseum 论文](https://arxiv.org/abs/2609.15983v2)，本报告不声称复现该框架。

## 二、为什么采纳这些方法

采纳理由来自跨会话交接的具体风险，而不是论文题目或作者声望。

1. **摘要会省略成立条件。** “检查通过”可能只表示四个样本通过。下一会话若只看到这句话，容易把样本支持当作完整验证。我们因此保存检查范围、覆盖类型、版本和原始回执。
2. **修订会改变证据适用对象。** 旧设计上的测试不能自动支持新设计。我们因此让定义和范围不可原地修改，检查始终指向确定版本。
3. **反例有明确的影响边界。** 一条论证失效，不等于所有结论都为假；另一条独立论证可能仍成立。我们因此记录必要前提和替代论证，按实际依赖重算支持状态。
4. **接手者需要复核入口。** 仅保存一个状态标签无法解释它为何成立。我们因此保留来源定位、证据正文和交接时与恢复时的状态差异。

以上是**我们从验证工作流作出的工程推导**。它们不由互信息不等式推出，也不意味着“最有信息的一比特”可以直接决定摘要长度、向量检索策略或记忆容量。

我采纳这些方法，是因为其中一部分能成为确定性的程序约束，另一部分能形成可被实验否定的模型行为假设。比如“抽样不能自动升级为完整验证”可以直接测试；“模型因此更少误用旧结论”则必须通过对照实验验证。

## 三、主要观点如何落地

| 采纳的方法及我们的推导 | 当前落地 | 实际保证与边界 |
| --- | --- | --- |
| 把结论与适用范围一起保存 | `ClaimInput` 保存定义、范围、前驱版本及来源；`CheckInput` 保存目标版本、检查器版本、覆盖和结果 | 范围按字符串精确匹配，不推断范围包含关系 |
| 不把抽样当完整验证 | `check record` 区分 complete、partial、unknown；超时和未知结果保留 | 核心采纳宿主提交的检查报告，不自行证明检查器可信 |
| 保留修订前的证据身份 | `claim add` 创建不可变后继；旧检查仍绑定旧版本 | 后继成功不会改写旧版本，也不会重定向旧依赖 |
| 将局部失败限制在相关依据内 | 同一 `argument` 的前提是共同必要条件；不同 argument 是替代依据；`claim explain` 重算状态和原因 | 依赖图维护支持关系；领域推导规则是否正确仍由宿主负责 |
| 让新会话能复查 | `handoff export/restore` 保留来源引用，核查原记录并比较新旧状态 | 权限由宿主单独传入；摘要或清单本身不授予权限；哈希不是对全库篡改者的身份认证 |
| 把模型建议与验证结果分开 | 研究宿主运行有限域检查器；运行时状态来自 Rust，独立 Python 计算器只用于事后评分 | 模型自己的错误判断原样保留，不由宿主改成正确答案 |
| 复查旧依据后再修订 | 研究宿主的 D 组强制补读，C 组提供同样信息但不强制 | 这是我们的可选干预，不是论文要求；会消耗动作预算 |

实现契约见 [版本化结论与证据](claims.md)，核心类型和接口见 [src/claims.rs](../src/claims.rs)。独立依据、范围、持久化和恢复场景见 [核心测试](../tests/claims.rs)及[独立进程 CLI 测试](../tests/claims_cli.rs)。研究宿主固定到[研究实现提交](https://github.com/lazyalexander/alpha-memory-research/tree/a852d04/bench)。

一个重要界限是：Rust 的 `verified` 表示收到了同范围完整支持报告，`supported` 表示存在有效论证；研究宿主会把符合领域规则的 `supported` 显示为 `verified`，并把失去依据区分为 blocked 或 invalidated。这不是新增了一份数学证明。

直接命中目标版本的反例优先于其他支持，冲突证据仍保留；不能因为还有另一条论证就忽略直接反例。版本 ID 是会话内标识，研究宿主显式选择共享研究账本，原始来源另受许可控制；恢复不会自动创建任意跨会话依赖边。单条 CLI 写入有事务，多条宿主调用不是分布式事务；失败时停止并留诊断，不承诺自动恢复。

## 四、用一个已实现的任务说明

任务输入为 $(a,b)\in\{0,1,2,3\}^2$，希望用缓存键保存乘积。

| 阶段 | 发生的事情 | 应保留的判断（研究宿主标签） |
| --- | --- | --- |
| 初筛 | 用 `a+b` 作键，只检查四个对角样本；另完整检查乘法交换性 | 键只得到 tested；依赖它的缓存与发布结论 blocked；交换性 verified |
| 反驳 | 提交 $(0,3)$ 与 $(1,2)$：键都为 3，乘积分别为 0 与 2 | 旧键 refuted；依赖它的缓存与发布结论 invalidated；交换性仍 verified |
| 修订 | 创建新的 tuple 键版本，检查全部 16 个输入，再建立新派生结论 | 新版本可得到支持；旧失败保留；新成功不修复旧证据 |
| 交接 | 新进程恢复明确交接引用，并核对被授权的来源 | 能追溯每项状态，旧交接遇新反例时能报告变化 |

这里的完整检查只覆盖上述有限域。不能把 16 个输入上的结果推广为无限整数域上的普遍证明。双重独立依据已经有核心确定性测试，但其未见模型任务尚未完成评测。

## 五、预期效果，以及如何判断预期落空

以下是后续评测要检验的预期，**不是已经实现的效果承诺，也不是第三步已经冻结的预注册指标**。

| 预期 | 观测方式 | 需要承认预期不足的情况 |
| --- | --- | --- |
| 减少把旧结论或抽样结果误报为已验证 | 固定模型、任务和预算，比较错误 verified、旧版本误用和范围错配；同时报告缺失判断 | 只减少输出、让任务更常中断，却声称错误率下降 |
| 反例后保留独立成立的依据 | 分别反驳两个替代论证，检查剩余论证与下游状态；另放入无关结论 | 第一条依据失效便误伤所有结论，或最后一条依据失效后仍保留支持 |
| 让下一会话更容易复核和正确续做 | 比较来源读取、状态判断、最终证据状态及三次交接完成率 | 能返回解释但模型仍误用，或证据已完成而交接失败 |
| 用更多信息换取更可靠的判断 | 完整统计请求、token、模型时间、原生 CLI 时间和存储量 | 可靠性收益未复现，或额外上下文和拒绝使完成率明显受损 |
| 让强制补读确实阻止危险修订 | 将 D 与同信息的 C 配对比较，区分主动读和拒绝后读 | 门槛只增加拒绝与预算耗尽，没有可观察的错误复用改善 |

核心的工程目标是在合成验收场景中做到版本绑定、权限及状态传播错误为零；这不等于承诺开放任务中的模型错误率为零。未来只有扩大未见任务后，才能估计效果及波动，届时再确定可接受的成本与完成率门槛。

## 六、目前有哪些证据

下表来自[第二步修订批次的脱敏记录](../bench/step2-ablation-revised.public.json)。每组只有种子 43/44，分母为每格 15 个必要判断；缺失判断保留在分母内。

| 组别 | 可见信息与约束 | 正确判断 / 30 | 缺失判断 | 完整工作流 / 2 | 总 token |
| --- | --- | ---: | ---: | ---: | ---: |
| A | 模型摘要及句柄 | 16 | 7 | 1 | 132,507 |
| B | A ＋原文检索 | 18 | 7 | 1 | 156,795 |
| C | B ＋原生状态、版本来源绑定和解释 | 30 | 0 | 2 | 243,318 |
| D | C ＋强制补读 | 23 | 7 | 1 | 303,335 |

这支持继续检验 C 类信息是否有用，**不支持已经确认 C 普遍优于其他组**。D44 在强制补读和格式拒绝后未能重提结论，最终预算耗尽；B44 证据已经完成却没有完成最后交接；A44 没有完成规定版本的完整验证。强制规则也可能损害工作流。

四组共用私有原生账本和检查器，比较的是模型可见信息与准入策略，不能单独识别 Rust、不可变存储或 C 组某一个信息字段的效果。首批八格的共用格式失败全部保留；修订批次的格式示例还与一项正确任务判断重合，因此两批不能解释为纯格式效果，更不能合并成独立的十六次有效性实验。详见[完整试运行报告](step2-report.zh-CN.md)与[协议修订说明](step2-protocol-amendment.zh-CN.md)。

工程证据是已记录的 83 项研究侧测试，以及两批共 16 格全部通过材料隔离、实际上下文和原生回执重放审计；这不等于 16 格任务都成功。Rust 核心本次没有变动，沿用此前 39 项测试及 Clippy 基线。原始模型材料留在本地；[公开材料清单](../bench/step2-materials.public.json)提供汇总与哈希。

## 七、当前取舍与后续落点

我的判断是继续采纳可复查的范围、证据、依赖与来源机制，因为这些机制既能落实为明确契约，也能暴露摘要掩盖的错误。C 类信息值得进入下一轮验证；是否默认启用 D 的强制补读，仍需要完成率和成本证据。

下一步按[开发计划](development-plan.zh-CN.md)冻结未见任务、评分器和新种子，覆盖双重依据、范围变化、旧交接遇到新反例及干扰项，再做同模型同预算对照。之后才检验 OpenCode 2.x 的实际捕获、压缩和恢复路径。Codex 的摘要与来源引用设计可以作为后续对照，不能替代本项目的证据账本。

最终希望交付的是一种可回答“这条结论针对哪个版本、在哪个范围、凭哪些证据成立，变化后还剩什么依据”的记忆能力。当前成熟度是受控研究原型，预期效果仍需未见任务和跨模型证据支持。
